# 線上帳號、資料與登入排查

## 選擇登入與保存方式

先分清楚：本機展示／瀏覽器存檔，不等於真正線上帳號和跨裝置進度。確認使用者想用帳號名稱還是 Email 登入、可用服務、費用、既有身份資料與部署環境。

Clerk＋Supabase 是墨境討伐的例子，不是所有專案的必選方案。Supabase Auth、Firebase Auth 等也可評估；Email／密碼登入不能直接宣稱已滿足「自訂使用者名稱／密碼」。若加使用者名稱對應，需設計唯一性、查找權限、濫用防護與帳號復原，不把登入密碼存到一般資料表或 Firestore 文件。

由認證服務管理密碼驗證。將不變的服務端身份 ID 對應遊戲資料，不以可改名的顯示名稱當資料主鍵。服務端密鑰不進瀏覽器、版本庫、技能包或手冊。

## 保存模型與權限

依產品需求建立個人進度、戰鬥、作答歷史、逐題掌握及外觀錢包。關鍵原則：

- 每個請求由服務端驗證登入，從驗證結果取得 user ID；不要信任客戶端送入的身份或 XP。
- 題目選擇、已解鎖單元、目前題號與答案在服務端核對，禁止跳題、跨帳號讀戰鬥、未解鎖進入。
- 同一有效作答的紀錄、HP、得分、錯題、XP 與解鎖應一起提交。使用事務／鎖或平台等效機制，不先發獎再寫歷史。
- 為有副作用操作設 request ID，定義重送是回傳同一結果還是可辨識衝突。抽卡及兌換遇網路不明結果，保留同一操作 ID 再確認，不產生新 ID 重扣。
- 在新增或遷移規則前備份與記錄；過去 XP 重算需經授權，依可信作答歷史重建，不把全部玩家歸零。
- 客戶端本機設定與待送結果不能取代服務端正式進度；重新登入以已成功結算紀錄恢復。

## 診斷「請先登入」

先確認使用者只要診斷還是也要修復。保留可重現步驟、發生題號、時間與非敏感錯誤。不要取得或要求學生密碼。

依序檢查：登入狀態是否就緒、請求是否附身份 token、token 是否過期、服務端認證是否有效、部署的 key／domain 是否一致、認證 middleware 或 proxy 是否涵蓋 API 路由。

Clerk `auth()` 無法偵測 middleware 時，依當前 Next.js／Clerk 官方文件核對檔名、位置與 matcher。若使用 src 結構，核對相應位置；不要盲目同時加入 middleware 與 proxy。先讀專案內隨版本附帶的文件，必要時查官方網站。

若已確認需要 token 更新，對每個請求取得目前 token；401 時最多額外刷新並重試 1 次，保留原 body 及 request ID。非認證錯誤、500、逾時或結果不明的寫入，不用同樣方式無限制自動重送。對重試結果再次出現未登入，停止重試並引導同帳號重新登入。

## 服務遷移

使用者詢問「換 Firebase 可不可行」只是詢問，不授權遷移。先說明身份 ID、密碼可移轉限制、進度映射、停機與回復方案。取得明確授權再處理服務建立、資料讀寫、環境設定與切換。

先用受控測試身份與本機／隔離環境驗證，不為方便在真實帳號抽卡、清空錯題或修改 XP。若正式驗證需要真實登入，由使用者操作或另行授權測試帳號。
