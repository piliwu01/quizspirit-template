# 正式站驗證、測試帳號清理與常見陷阱（2026-11-19 案例整理）

## 部署交接流程（使用者自行部署時）

1. 本機完成：全部測試通過、`npm run build`、無頭瀏覽器在多種尺寸實際操作（至少 1920×1080、1366×768、390×844；版面敏感時加 1280×720、1024×768、360×740）。
2. 打包 zip（檔案放在 zip 根目錄），用 SendUserFile 傳給使用者，附一句部署方式（例：解壓縮覆蓋到專案資料夾，雙擊 deploy.bat）。不要只說「已完成」，要說「還沒上線」。
3. 使用者回「好了」後，才到正式網站驗證；驗證完刪除測試資料並回報剩餘帳號數。
4. 若 deploy.bat 不會套用 D1 migration，新資料表要另外建立：用 Cloudflare 連接器執行 `CREATE TABLE IF NOT EXISTS ...`，建好回報筆數為 0、原有資料沒動，並把 SQL 同步存進 `migrations/`。

## 正式站驗證做法

- 用 Cloudflare 連接器直接在 D1 插入臨時帳號（帳號前綴固定，如 `zztest-`；密碼雜湊事先產生；`must_change=0`），再插入一筆 progress（已選夥伴的新狀態）。放在真實班級才能測到題庫與同班功能；放在沒有題庫的班級會拿到備援數學題。
- 在內建瀏覽器的頁面內用 `fetch('/api/login')` 登入，再 reload 進入畫面；需要特定畫面尺寸時用 resize_window，測完重設為 desktop。
- 用頁面內 JS 量測（`getBoundingClientRect` 是否重疊、`scrollHeight` 是否等於視窗高、computed font-size），比截圖可靠。隱藏的瀏覽器面板截圖常是舊畫面或動畫凍結的畫面；有疑慮就再截一次或讀 DOM。
- 需要「答對」的情境：題目答案不會送到前端，就逐一試選項直到出現「答對了」，記錄前後血量。
- 隨機情境（例如相剋提示）用迴圈重開戰鬥直到出現，記錄每次的雙方屬性。
- 伺服器端狀態（如抽題紀錄）直接查 D1 progress 的 JSON 驗證。

## 清理（每次驗證後都要做）

依外鍵順序刪除：交易、sessions、operations、討伐／PVP 成員與房間、activity_locks、progress、AI 用量、英雄榜獎勵 → 最後刪 `users WHERE username LIKE 'zztest-%'`。刪完查詢總帳號數，與原本數量比對後回報。

## 常見陷阱

- **按鈕按下位移**：全站 `button:active{transform:translateY(2px)}` 會覆蓋用 `translateY(-50%)` 置中的固定按鈕，按下瞬間按鈕跳開，mouseup 落在別的元素，click 不成立。為該按鈕另寫 `:active{transform:translateY(calc(-50% + 2px))}`。
- **固定側欄被覆蓋**：抽屜／側邊標籤用 `createPortal` 放到 body，避免被父層 stacking context 擋住。
- **Worker 圖片快取**：圖存在 D1、Worker 用 Cache API 快取 1 小時；直接改 D1 的圖要等快取過期，告訴使用者大約何時生效、可 Ctrl+F5。
- **圖片產生 Worker 的 CPU 上限**：在 Worker 內 base64 解碼大圖會觸發 1102；改成回傳 b64 由瀏覽器解碼，再把原始位元組上傳。產圖頁面不要重用正在產圖的分頁。
- **本機伺服器**：回覆結束後背景程序會被停止；每次測試前重新啟動。反覆登入會觸發登入限制，測試前清空本機的登入限制表。
- **測試的隨機性**：涉及傷害下限的測試要固定對手屬性，否則被剋 ×0.8 時偶爾失敗。新增測試後重跑整套數次確認沒有隨機失敗。
- **英文回覆**：使用者明確要求全程繁體中文；工具輸出是英文時，回覆仍用中文。
